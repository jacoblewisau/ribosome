# Story 0004

## Role, behaviour, outcome

As a user of the todo list, I want to fix a todo's text without deleting and re-adding it, so I can correct typos and refine descriptions in place.

## Acceptance criteria

1. The text of an existing todo can be edited by activating an edit mode on that specific TodoItem. Activation: clicking the text span. The text span is the click target; clicking elsewhere on the TodoItem (the checkbox, the tags region, the date, the remove button) does NOT enter edit mode.
2. While editing, the text is replaced by a labelled text input pre-filled with the current text. The input receives focus immediately. The `TodoItem` root exposes `data-verify-editing="true"` while editing; `data-verify-editing="false"` otherwise.
3. Pressing Enter while the input is focused commits the edit IF the trimmed value is non-empty. The todo's text becomes the trimmed value. Edit mode ends. `data-verify-editing` returns to `"false"`.
4. Pressing Enter while the trimmed value is empty cancels the edit (the original text is preserved). The todo's text does not change to empty. Edit mode ends.
5. Pressing Escape while the input is focused cancels the edit. The todo's text is unchanged. Edit mode ends.
6. Clicking outside the input (the input loses focus) cancels the edit. The todo's text is unchanged. Edit mode ends.
7. After save or cancel, focus returns to the text element of the same TodoItem.
8. Two or more TodoItems may be in edit mode simultaneously. Their states are independent.
9. Entering edit mode does not mutate any other todo's state. No item is toggled, removed, or reordered as a side effect of editing.
10. The pure feature module gains a `setTodoText(state, id, text)` helper that returns a new state with the trimmed text on the matching todo. Whitespace-only text is rejected; the helper returns the input state unchanged in that case.
11. Existing acceptance criteria and contract invariants continue to hold. Existing fixtures pass unchanged because `data-verify-editing` is additive and defaults to `"false"`.

## Edge cases

- Editing then immediately blurring (no typing): the original text is preserved; edit mode ends.
- Editing then typing whitespace-only then Enter: cancel (criterion 4).
- Editing then pressing Enter with the same text as before: commits, ends edit mode. Idempotent.
- Editing while the todo's `done` is toggled by another agent (not possible in this single-user UI but stated for completeness): the edit input keeps its own value; on save, the new text replaces only the text field, not done.
- A todo with very long text: edit input scrolls horizontally; no truncation rules added.

## Out of scope

- Editing tags or due date inline. Future story.
- Undo / redo across edits.
- Multi-line text. Single-line input only.
- Edit history. The todo retains only its current text; no audit log.
- Animations or transitions on the input mount/unmount.
- Mobile gesture handling beyond what HTML inputs provide natively.
- Persistence across reloads (separate future story).

## Open questions

None. The five questions from the researcher's findings resolve to the defaults stated above:

1. Click-outside cancels (criterion 6); matches Linear / GitHub / Notion inline-edit UX.
2. Whitespace-only Enter cancels (criterion 4); mirrors the form's existing whitespace guard.
3. Concurrent edits across items are allowed (criterion 8); per-item local state.
4. Focus returns to the text element after save / cancel (criterion 7).
5. Click target for entering edit mode is the text span only (criterion 1).

If `/approve`, the assumptions stand.
