# tests/verify

The contract harness for Ribosome. Borrowed from `how-we-claude-code` phase 3
with deliberate divergences documented in
`.claude/skills/verify-contracts/SKILL.md`.

## Files

- `last-run.json` (gitignored, regenerated by `npm run verify`). The canonical
  report consumed by the `validator` subagent. Schema: `ribosome.verify.report`,
  version `1`. Field definitions are in `src/verify/core/types.ts` (`VerifyReport`,
  `FixtureResult`, `Check`). Field semantics and consumption protocol are in
  `.claude/skills/verify-contracts/SKILL.md`.

## Running

```
npm run verify
```

The script runs Vitest against `src/verify/matrix.test.ts` with happy-dom.
The matrix walks the registry, runs every unit-fixture-verifier triple,
asserts pass conditions (every unit has at least one probe; every non-probe
verdict is PASS), and writes `last-run.json` from an `afterAll` hook.

## Debugging a failed verify

1. Read `last-run.json`. Each `FixtureResult` with `verdict: "FAIL"` lists the
   failing checks in `checks[]` with `status: "fail"` and a `reason` string.
2. The `domSnapshot` field shows the actual observed `data-verify-*` attributes
   on the unit's root element. Compare to the spec's expected values.
3. Vitest's stdout shows the assertion message and the file:line of the
   matrix test that caught the failure.
4. If a fixture genuinely fails, the corrective action is to fix the unit or
   the fixture, not the harness. The harness is the witness.
