# Story 0002

## Role, behaviour, outcome

As a user of the todo list, I want to attach short categorising tags to each todo, so that I can group related items at a glance and (in a future story) filter by tag.

## Acceptance criteria

1. Each todo carries an ordered list of zero or more tags. Tags are short strings.
2. The form accepts tags entered as a comma-separated string in a dedicated input field labelled "Tags". The text input remains required; the tag input is optional.
3. Submitting the form with both fields parses the tags by splitting on commas, trimming each part, dropping empty parts, and deduplicating exact-match duplicates (case-sensitive). The new todo carries the deduplicated tag list.
4. After submission, both inputs clear.
5. Each TodoItem renders its tags inline after the text. The tags are exposed under `data-verify-field="tags"` on a wrapping element; the value is the tag list joined by ", " (or empty string when there are no tags).
6. The TodoItem's `data-verify-unit="TodoItem"` element gains a `data-verify-tag-count` attribute carrying the number of tags as a string.
7. The TodoApp `data-verify-unit="TodoApp"` element gains a `data-verify-tagged` attribute carrying the number of todos that have at least one tag.
8. The tag input is associated with a `<label>` element so the a11y verifier does not surface a new finding.

## Edge cases

- Empty tag input string: the todo has zero tags. `data-verify-tag-count="0"`.
- Whitespace-only tag input: parsed as zero tags (every part is empty after trim).
- All-duplicate tag input ("urgent, urgent, urgent"): parsed as one tag.
- Mixed-case duplicates ("Urgent, urgent"): kept as two distinct tags (dedupe is case-sensitive per the resolution).
- Tag containing a comma cannot be expressed (the delimiter is global). Out of scope.
- Maximum tags: unbounded for now (no cap).

## Out of scope

- Tag filtering. Tags become filterable in a follow-up story.
- Tag editing on existing todos. New tag list is set at creation only.
- Tag styling (chips, colours). Plain text rendering only.
- A separate TagInput component. The tag input lives inside TodoForm.
- A tag count in TodoStats. Out of scope per researcher Q5.
- Tag deletion as an independent action. Removing the todo removes its tags.
- Server-side persistence. None of this is wired to a backend.

## Open questions

None. The five open questions from the researcher resolve to the defaults stated above:
1. Single comma-separated text input (researcher's simplest option).
2. Case-sensitive exact-match dedupe (researcher's simplest option).
3. No max-tag cap (unbounded; tag display will cope visually for now).
4. Tags render inline after text, comma-separated, with `data-verify-field="tags"`.
5. TodoStats unchanged.

If the operator `/approve`s, the assumptions above stand.
