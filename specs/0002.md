# Spec 0002

Story: stories/0002.md

## Path selection

`full`. New field on Todo, new UI input, new probe.

## Data model changes

`Todo` (in `src/features/todos/todos.feature.ts`) gains:

- `tags: ReadonlyArray<string>` (default empty array).

`addTodo` signature changes from `(state, text, now?)` to `(state, text, tags, now?)`. `tags` defaults to `[]`. Whitespace-only tag entries are filtered out by the parser before reaching `addTodo`, so `addTodo` itself does not need to handle parsing.

New helper:

- `parseTagsInput(input: string): string[]`. Splits on `,`, trims each part, drops empty parts, deduplicates case-sensitive exact matches preserving first-seen order. Pure, no side effects. Located in `todos.feature.ts`.

## API or background flow

None.

## UI changes

### TodoForm
- A second labelled input field `id="todo-tags"` with `<label htmlFor="todo-tags">Tags</label>`.
- The input has `data-verify-input="todo-tags"`.
- The form's submit handler calls `parseTagsInput` on the tag input value and passes the resulting array as the third argument to `onSubmit`.
- `onSubmit` prop signature changes from `(text: string) => void` to `(text: string, tags: string[]) => void`.
- Both inputs clear after submit.
- TodoForm gains `data-verify-tags-input-length` and `data-verify-parsed-tag-count` attributes for observability.

### TodoApp
- The `onSubmit` callback to `TodoForm` updates to pass tags to `addTodo`.
- The root `data-verify-unit="TodoApp"` element gains `data-verify-tagged` attribute, the count of todos with at least one tag.

### TodoList
- Unchanged. It still maps todos to `TodoItem`.

### TodoItem
- After the `<span data-verify-field="text">`, render a wrapper containing the tags inline. The wrapper carries `data-verify-field="tags"` and its text content is the tags joined by ", " (empty string if no tags).
- The root `data-verify-unit="TodoItem"` element gains `data-verify-tag-count` attribute (the array length as a string).

### TodoStats
- Unchanged (per story Out of Scope).

## Tests required

### Contract spec updates

`src/verify/specs/TodoApp.verify.ts`:

- Existing fixtures unchanged. Their invariants do not reference tags, so default tagged=0 keeps them green.
- Add a new fixture `with-tags-on-some-items`: drives the form to submit two todos, one with tags ("urgent, follow-up") and one without. Asserts `data-verify-tagged="1"` on the TodoApp root. Asserts the first TodoItem element exposes `data-verify-tag-count="2"`.

`src/verify/specs/todos.feature.verify.ts`:

- Add a probe fixture `tags-dedupe-fails`: claims that parsing "x, x, x" yields three tags. The invariant asserts `data-verify-tag-count === "3"` on a freshly-created todo. Since parseTagsInput dedupes to one tag, the actual attribute will be "1" and the invariant fails. Verdict PASS (probe). Confirms the dedupe path is exercised.
- (Optional, included) Add a non-probe fixture `tags-parse-and-trim`: drives the form with "  a  , b  ,, c  , a" and asserts `data-verify-tag-count="3"` (a, b, c) on the resulting TodoItem.

### Unit tests

None (the contract harness is sufficient; the pure parser is exercised indirectly via the fixtures).

## Risks

- Type-signature change to `addTodo` is a breaking-change-equivalent within this repo. Every call site (currently only `TodoApp.tsx`) must update. The contract specs that call `addTodo` directly (`todos.feature.verify.ts:add-rejects-empty`, `add-rejects-whitespace`) must update too. Builder must check.
- a11y: the new tag input must have a label. The spec mandates this explicitly to prevent the regression.
- DOM contract: adding new attributes is non-breaking; existing fixtures that do not reference them keep passing.
