# Story 0003

## Role, behaviour, outcome

As a user of the todo list, I want to give a todo an optional due date and see at a glance which todos are overdue, so that I can prioritise the items that are running late.

## Acceptance criteria

1. Each todo can carry an optional due date (a calendar day, no time component visible to the user). A todo with no due date renders without a date.
2. The form provides a third labelled input (`Due`) for the date. The text input remains required; the tag input and the date input are optional.
3. Submitting the form parses the date input. An empty date input means the new todo has no due date. A non-empty date input is interpreted as the local-noon timestamp of the chosen date (avoiding the off-by-one-day surprise that UTC-midnight parsing causes in Australian and west-of-UTC time zones).
4. After submission, all three inputs clear.
5. Each `TodoItem` whose todo has a due date renders the date as text under `data-verify-field="due-date"` (formatted `YYYY-MM-DD` for machine reading; the visible text matches).
6. A `TodoItem` is "overdue" when its todo has a due date strictly less than the current resolved time AND the todo is not done. The `TodoItem` root carries `data-verify-overdue="true"` exactly in that case; otherwise `data-verify-overdue="false"`. Marking a todo done removes its overdue status even if the date is still in the past. (A done todo is never overdue.)
7. Overdue items also carry an aria-label suffix `". Overdue."` on the `<li>`'s label (the existing toggle-aria-label is replaced with a more descriptive form that includes the overdue suffix when applicable) so the overdue state is conveyed without colour.
8. The `TodoApp` root carries `data-verify-overdue-count` (number, as string) listing how many todos are currently overdue.
9. The `TodoStats` element gains a `data-verify-overdue` attribute carrying the same count, and renders a fourth visible chunk: `<span data-verify-field="overdue">N overdue</span>` after the existing total/done/active spans.
10. The filter controls gain a fourth option `overdue` (alongside `all`, `active`, `done`). Selecting it makes `visibleItems` return only currently-overdue todos.
11. Date math is deterministic. `TodoApp` accepts an optional `now?: () => number` prop (default `() => Date.now()`). Fixtures inject a fixed clock to assert overdue behaviour reproducibly. `now()` is resolved once per render and passed down as a plain number (`nowMs`) to children that compute overdue.
12. Existing fixtures continue to pass. New attributes are additive; the new filter option does not change default behaviour.

## Edge cases

- Empty date input: todo has no due date; `data-verify-overdue="false"` always.
- Date input in the future: not overdue.
- Date input exactly equal to `nowMs`: not overdue (strict less-than).
- Todo with past due date but done=true: not overdue.
- Toggling a todo from done back to active when its due date is in the past: becomes overdue. (`isOverdue` recomputes from inputs.)
- Filter "overdue" with no overdue todos: list renders empty.
- Multi-day-ago due dates: still overdue (no "stale" threshold).

## Out of scope

- Time-of-day on due dates. Only calendar days.
- Editing a due date after creation.
- A ticker that re-renders to flip overdue status at the moment a date passes. The substrate re-renders on state changes only; that is acceptable.
- Per-todo notifications, sorting by due date, calendar UI.
- Persisting todos across reloads (separate future story).
- Visual styling rules (colour, font weight). Only the contract attribute and aria-label are guaranteed; styling is incidental.

## Open questions

None. The five open questions from the researcher resolve to the defaults stated above:
1. Local-noon timestamp parsing.
2. `now?: () => number` prop on TodoApp.
3. Overdue count in TodoStats included.
4. No live ticker (out of scope).
5. Overdue = (dueDate strict-less-than nowMs) AND (done === false).

If `/approve`, the assumptions stand.
