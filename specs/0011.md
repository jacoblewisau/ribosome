## The drift, and which way to fix it

The CLAUDE.md Stack table reads:

```
| Runtime | Node 22 (`engines` in package.json), bash 3.2+ for hooks |
```

The parenthetical claims the Node 22 requirement is declared via an `engines`
field in `package.json`. No such field exists today: `package.json` carries only
`name`, `private`, `version`, `type`, `description`, `scripts`, `dependencies`,
and `devDependencies`. The requirement itself is real (every workflow pins
`node-version: "22"` and every script uses `--experimental-strip-types`, a Node
22+ feature); only the `engines` declaration is missing.

The issue offers two fixes: remove the parenthetical from CLAUDE.md, or add the
`engines` field to `package.json` (the issue's stated preferred option, since it
also aids `nvm` and Volta). This spec takes the second. Reason: CLAUDE.md is
maintainer-owned and an agent is charter-forbidden to edit it ("No edits to
CLAUDE.md from an agent" in the do-not-do list; rule-miner is the only path).
Adding the field reconciles code to doc, which is buildable by the builder, and
makes the existing CLAUDE.md sentence accurate rather than deleting it.

## The change

Add an `engines` field to `package.json` declaring the Node runtime floor:

```
"engines": { "node": ">=22" }
```

`>=22` is the value the issue proposes and matches the Stack table's "Node 22"
(read as "Node 22 or newer"). It is advisory by default: npm does not refuse an
install on an engines mismatch unless `engine-strict=true` is set in an `.npmrc`,
and no such file is added here, so the field changes nothing about how installs
or CI behave. It is purely a declaration that tools like `nvm` and Volta and a
maintainer reading the manifest can rely on. No dependency is added or moved, so
the lockfile (if present) is untouched.

Placement: insert `engines` after `description` and before `scripts`, the
conventional position for a top-level metadata key.

## Risks

- **engine-strict surprise.** If the repo (or a contributor) later sets
  `engine-strict=true`, the field would start enforcing and could block an
  install on Node < 22. Mitigation: that is the intended requirement (the repo
  already pins Node 22 everywhere); the field only makes an existing constraint
  explicit, and no `.npmrc` is added here so behaviour is unchanged today.
- **Value drift from the doc.** If someone later changes CLAUDE.md to a
  different Node floor, the field and the doc could disagree. Mitigation: the
  acceptance test pins `>=22`, so a doc change to a different floor would surface
  as a failing test prompting the field to be updated in lockstep.
